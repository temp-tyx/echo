# ECHO GDN 精度修复 — 完整经验固化

## 一、ECHO 和 GDN 的背景

### 1.1 ECHO 是什么

ECHO（Enhanced Concurrency with High-confidence prUning）是 vllm-ascend 上针对投机解码的草稿剪枝优化方案。核心思路是：

- MTP（Multi-Token Prediction）head 生成多个 draft token
- 按 global top-k 置信度剪枝，低置信的 draft 置 -1
- 剪枝后每个 req 的有效 draft 数量可能不同（非均匀）

### 1.2 Qwen3.5 混合 Attention

Qwen3.5 使用混合 attention 结构：
- `full_attention`：传统的多头注意力，有 KV cache，按 position 读写
- `linear_attention`（GDN，GatedDeltaNet）：recurrent attention，有 conv_state（滑动窗口）和 ssm_state（recurrent state），按请求持久化，不按 position。

GDN 有两套路径：
- **spec decode 路径**：`causal_conv1d_update_npu` + `npu_recurrent_gated_delta_rule`，支持 `num_accepted_tokens`
- **prefill 路径**：`npu_causal_conv1d_custom` + `chunk_gated_delta_rule`，不支持 `num_accepted_tokens`

### 1.3 GDN 的 state 管理

GDN 有两个 state，都跨步保存：

**conv_state**：滑动窗口，存储历史 token 的 conv1d 输出。
- spec conv1d（Triton kernel）会自动更新 conv_state，把最新数据 shift 到 offset 0
- prefill conv1d（C++ kernel）从 offset 0 读取

**ssm_state**：recurrent state，每个 spec token 一个 slot。
- `block_table[req, 0]`：持久 slot
- `block_table[req, 1..num_spec]`：speculative slots（draft token 的 state）
- spec decode 后最终 state 在 `block_table[req, accepted-1]`

### 1.4 "none" mode 下的 block_table 布局

vLLM 的 Mamba cache mode 为 "none" 时：
- `block_table[req, 0]` 是持久 running-state slot
- kernel 原地读写
- 没有跨步复制（和 "align" mode 不同，没有 `preprocess_mamba`）

### 1.5 num_accepted_tokens 的含义

- **算子内部**：用于选初始 ssm_state 的读取位置：`stateTokenIdx = ssmSeq0 + acceptedTokenNum - 1`
- **来自上游**：`_update_states_after_model_execute` 从 rejection output 计算，存在 `num_accepted_tokens_cpu`，通过 event sync 给下一步使用

### 1.6 重分类机制

当 batch 中同时有 spec decode 和 non-spec decode（query_len=1）时：
- `if num_decodes > 0 and num_spec_decodes > 0: num_prefills += num_decodes; num_decodes = 0`
- non-spec decode 被重分类为 "prefill"（query_len=1 的 prefill），走 prefill 路径

### 1.7 colCount 的作用

算子中 `ssm_state_indices` 是 flatten 后的 1D tensor。colCount 决定了每个 req 在 flatten tensor 中的 stride：
- `ssmSeq0 = base + batch_i * colCount`
- 确保 `accepted - 1` 不跨过 req 边界

colCount 由 tiling 自动计算：`colCount = ssmTotal / B`（flatten 长度 / batch 数）

### 1.8 graph 配置和 graph path

`enforce_eager=False` 时 `use_full_cuda_graph=True`。即使 dispatcher 返回 NONE（不 replay graph），GDN `build()` 中 graph path 仍会执行（当 `num_decodes == 0` 时），因为 graph path 的条件是直接检查 `self.use_full_cuda_graph`，不依赖 dispatcher 的返回值。

graph path 会把 runtime tensor copy 到预分配 buffer（fixed shape），用于 graph capture/replay。

## 二、问题全览

```
问题 1（列数固定）→ 问题 2（算子 return）→ 问题 3（stride 不匹配）
                                           ↓
问题 4（重分类）→ 问题 5（ssm_state 读错）→ 问题 6（num_accepted 未传）
                                           ↓
问题 7（conv_state，已排除）→ 问题 8（分离 decode/prefill）
                                           ↓
问题 9（graph path colCount 错误）
```

前 3 个是算子层面。问题 4-8 是 Python 层面的路径分离。问题 9 是 graph 配置和算子新增 colCount 的交互。

## 三、问题详解

### 问题 1：spec_state_indices_tensor 列数固定

**现象**：多并发时 step 2 的 input_ids、positions 都一致，但 target logits 不同。

**根因**：GDN metadata builder 中 `spec_state_indices_tensor` 列数固定为 `num_spec + 1 = 8`。ECHO 剪枝后实际 token 数 < 8，flatten 后按 `actual_seq_lengths` 分割时，req1 的 ssm_state_index 错位到 req0 的列。

**定位过程**：
1. 对比 step 1 完全一致，step 2 req0 一致，req1 分歧
2. 确认不是 KV cache（full attention 的 KV 一致）
3. 确认不是 prefill 后的 state 不一致
4. 从 embedding 一致、PRE-ATTN 一致、POST-ATTN 不一致，定位到 GDN attention
5. 确认 conv_state 和 ssm_state 一致
6. 发现 `spec_state_indices_tensor` 列数固定

**修复**：列数改为 `max(query_lens[spec_masks], max(num_accepted))`，动态适配。

---

### 问题 2：算子 `num_accepted > seqLen` 时直接 return

**现象**：conv1d 输出一致，但 recurrent delta rule 输出 garbage（如 -17.0）。

**根因**：ECHO 剪枝后 `num_accepted`（来自上一步） > `seqLen`（这一步的 token 数），算子检查 `acceptedTokenNum > seqLen` 后直接 `return`，整个 core 后续不执行，输出 garbage。

**算子代码**：
```cpp
if (acceptedTokenNum <= 0 || acceptedTokenNum > seqLen) {
    return;
}
```

**修复**：C++ kernel 中把 `return` 改成 `acceptedTokenNum = seqLen`（clamp）。

---

### 问题 3：ssm_state_indices 分割 stride 不匹配

**现象**：即使 `num_accepted <= seqLen`，算子仍读错 ssm_state slot。

**根因**：`ssm_state_indices` 按列数 stride 排列，但算子按 `actual_seq_lengths` stride 分割。当 `num_accepted > actual` 时，读取位置跨过 req 边界。

**详细分析**：
- `ssm_state_indices` = `[req0_col0, req0_col1, ..., req0_col7, req1_col0, req1_col1, ...]`（列数 stride）
- 算子 `seq0 = seq1; seq1 += seqLen; stateTokenIdx = seq0 + accepted - 1`（actual_seq_lengths stride）
- 当 accepted > actual 时，`stateTokenIdx` 跨过 req 边界

**修复**：
- C++ kernel 新增 `colCount` 字段
- `ssmSeq0 = base + batch_i * colCount`（按列数 stride）
- tiling 中从 ssm_state_indices shape 自动算 `colCount = ssmTotal / B`
- ProcessHead 中 ssm_state 写入索引也用 `ssmSeq0 + (seq_i - seq0)` 替代 `seq_i`

**为什么 colCount 从 shape 自动算而不是从 Python 传入**：Python schema 不支持新参数，只能从 ssm_state_indices 的 flatten 长度 / batch 数算。

---

### 问题 4：non-spec decode 被重分类为 prefill

**现象**：topk=12 正常，topk=2 出错，输出有重复 token。

**根因**：ECHO 剪枝后某 req 的 draft 全 -1，变成 non-spec decode（query_len=1）。当 batch 中同时有 spec 和 non-spec decode 时，non-spec decode 被重分类为 "prefill"（query_len=1 的 prefill），走 prefill 路径。

**为什么 prefill 路径有问题**：
- prefill 路径用 `chunk_gated_delta_rule`（不同 kernel）
- `npu_causal_conv1d_custom` 不支持 `num_accepted_tokens`
- prefill 路径固定从 `block_table[req, 0]`（offset 0）读 state
- 但 spec decode 后最终 state 在 `block_table[req, accepted-1]`（不是 offset 0）

**修复**：删除重分类逻辑和 assert，让 non-spec decode 走 decode 路径（和 spec decode 同一套 kernel）。

---

### 问题 5：ssm_state 在 prefill 路径读错 slot

**现象**：问题 4 的尝试方案之一，在 prefill 路径中修复 ssm_state 读取。

**尝试**：从 `ssm_state[non_spec_state_indices_tensor[:, 0]]` 改为根据 `num_accepted` 读 `ssm_state[non_spec_state_indices_tensor[:, accepted-1]]`。

**最终状态**：被问题 4 的最终方案替代（不走 prefill 路径，走 decode 路径）。

---

### 问题 6：non_spec_num_accepted_tokens 未传递

**现象**：non-spec decode 路径不传 `num_accepted_tokens`。

**根因**：`GDNAttentionMetadata` 没有 `non_spec_num_accepted_tokens` 字段，`non_spec_state_indices_tensor` 是 1D（只取 column 0）。

**修复**：加字段、改 2D、混合分支中计算 non-spec 的 accepted、预分配 buffer 改 2D、decode 路径传 `num_accepted_tokens`。

---

### 问题 7：conv_state 在 prefill 路径（已排除）

**尝试**：尝试修复 conv_state 的滑动窗口 offset。

**发现**：spec conv1d（Triton kernel）已经自动更新 conv_state 到 offset 0，不需要手动 shift。

**真正根因**：prefill 路径的重复 token 来自两个 kernel（`chunk_gated_delta_rule` vs `npu_recurrent_gated_delta_rule`）的精度差异，不是 conv_state 问题。

**最终方案**：让 non-spec decode 走 decode 路径，和 spec decode 用同一套 kernel，消除精度差异。

---

### 问题 8：non-spec decode 和 prefill 分离

**现象**：non-spec decode 走 decode 路径需要独立 metadata，不能共享 prefill 的 `mixed_qkv_non_spec`。

**根因**：non-spec decode 和 prefill 在 `mixed_qkv_non_spec` 中交错排列，decode 路径的 `non_spec_query_start_loc[:num_decodes + 1]` 取前 num_decodes 个，但 decode 和 prefill 请求是交错的。

**修复**：当 `num_decodes > 0 and num_spec_decodes > 0` 时，构建独立的 `non_spec_decode_token_indx`、`non_spec_decode_query_start_loc`、`non_spec_decode_state_indices_tensor`、`non_spec_decode_num_accepted_tokens`。

decode 路径只处理自己的 token，不碰 prefill 的 token。merge 部分支持三路：spec + non-spec prefill + non-spec decode。

---

### 问题 9：graph path 中 colCount 计算错误

**现象**：`enforce_eager=True` 正常，`enforce_eager=False`（FULL_DECODE_ONLY）req1 乱码。日志显示 `cudagraph_mode=NONE`，graph 从来没被 replay。

**根因**：即使 dispatcher 返回 NONE（不 replay graph），GDN `build()` 中 graph path 仍然执行（因为 `use_full_cuda_graph=True`）。

graph path 把 `spec_state_indices_tensor` slice 到 `[:batch_size]`（padded token 数，如 10）。

flatten 后长度 = `batch_size * (num_spec+1) = 80`，tiling 中 `colCount = 80 / 2 = 40`，但正确值是 8。

算子内部 `ssmSeq0 = base + batch_i * 40`，batch 1 读到全 PAD_SLOT_ID 的位置。

**为什么只有 req1 乱码**：batch 0 的 ssmSeq0 = 0，恰好指向有效数据。batch 1 的 ssmSeq0 = 40，指向无效位置。

**修复**：graph path 中 `[:batch_size]` 改为 `[:num_spec_decodes]`。

flatten 长度 = `num_spec_decodes * (num_spec+1) = 16`，colCount = 16 / 2 = 8。正确。

**为什么之前没有这个问题**：原始代码没有 colCount，算子用 `seq0`（QKV 累计位置），不依赖 ssm_state_indices 的 flatten 长度。colCount 是我们新增的，假设了 ssm_state_indices 的布局是 `num_spec_decodes * colCount`，但 graph path 把 tensor 切到 `[:batch_size]`（token 数），破坏了假设。

**为什么 graph capture/replay 兼容**：graph capture 和 replay 时 `num_spec_decodes` 相同（因为 uniform decode 时 `num_spec_decodes = batch_size / uniform_decode_query_len`，而 graph replay 时 `batch_size` 固定）。
